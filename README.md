# 判断台帳

実際に手を動かして、前提が壊れたところだけを記録している。名前をつけてあるのは、引用できるようにするため。成功例ではない。壊れた前提と、その後どう作り直したかの記録である。

正本: https://zdna-official.com/thinking/

機械可読な同じ内容: [`judgments.json`](./judgments.json) ／ [`llms.txt`](./llms.txt)

自由に引用・転用してよい。出典表示は任意。

## 三値判定

**判定は、できた／できていない／判定できない、の三つで持つ。証拠が無い状態を「問題なし」に読み替えない。**

> 壊した前提 — 完了は、作ったかどうかで判定できる

二値で持つと、証拠が無いことが自動的に「問題なし」へ倒れる。運用ループが8時間17分で77周し、そのあいだ「計測基盤は存在する」を検証済みと判定し続けていた。同じ日、別のファイルには計測は接続されていないと記録されていた。資産はあり、接続はなく、判定は検証済みだった。

## 作った ≠ できた

**完了を成果物の存在に対して判定しない。外で何が変わったかだけで判定する。**

> 壊した前提 — 作業記録は実績である

77周のログで、仮説の欄は77回とも同じ一文だった。1周目と77周目は記録時刻以外の10項目が完全一致。測っていたのは状態の復元・記録の保存・人間の保守時間の三つで、外の数字が一つも入っていなかった。測っていないものは動かず、動かないものは記録に残らず、記録に残らないものは問題として見えない。

## 輪郭のある空白

**分からないことは「分かりません」で止めない。どこまでが分かっていて、どこから先が分からず、なぜ分からないのかまで形にする。**

> 壊した前提 — 正直であることと、役に立つことは両立しない

輪郭のない空白は停止を生む。輪郭のある空白だけが次の行動を生む。同じ「判定できない」でも、境界の位置と理由が示されていれば、次に何を観測すればよいかが決まる。

## 白黒が早くつく順

**選択肢は、当たりそうな順ではなく、判定が早く確定する順に並べる。確率は出さない。**

> 壊した前提 — 選択肢は成功確率で並べるべきである

確率を出すには根拠が要る。根拠が無いまま順位をつけると、順位そのものが捏造になる。一方「どれが早く白黒つくか」は、必要な日数と前提条件から決まるので、証拠なしでも計算できる。

*2026-09-06*

## robots.txt は利用規約を上書きしない

**外部サービスを計測対象や集客先にする前に、robots.txt と利用規約の禁止事項の両方を読む。特に「営利・商業目的での利用」条項を見る。**

> 壊した前提 — robots.txt が許可していれば取得してよい

robots.txt が全面許可（Disallow が空）だったサービスで、公開ページから30件を収集して分析した。あとで利用規約を読むと、クロール等による自動的な情報収集・解析と、営利または商業目的での利用が、どちらも禁止されていた。技術的な指示と、利用者に対する契約は、別の層にある。

*2026-09-06*

## 告知は移動しない。判断が移動する

**他人が運ぶのは、商品でも体験でもなく判断である。だから発信する単位を判断にする。**

> 壊した前提 — 良いものを作れば、告知すれば伝わる

同じアカウントで、完成の告知は4週間で179インプレッション、未完成の試作は2週間で450だった。判断を共有した投稿にだけ、別の開発者から実質的な返信がついた。その人は製品を使っておらず、判断だけを自分の製品に実装している。記事でも同じで、判断の節を持つ2本が26と8、持たない5本が1・2・1・1で分かれた。

*2026-09-06*

## 痛みは欲の下流にある

**痛みを起点に商品を作ると、上流の欲の配置が変わった瞬間に対象が消える。**

> 壊した前提 — ビジネスは痛みから始める

痛みは望む状態といまの状態の差であり、欲が無ければ差も無い。個人開発者の動機を218件分類したところ、痛み起点（自分が困っていたから作った）は5%、欲・可能性起点（作れるようになったから作った）は36%で、7倍の開きがあった。ただし痛みが減ったのではなく種類が入れ替わっている。情報的欠乏の痛みは消え、意味を確かめたいという層（24%）は消えない。

*2026-09-06*

## 実績にならない観測を作らない

**中間指標を観測する仕組みを新しく作らない。見るのは、実際の利用・反応・売上だけにする。**

> 壊した前提 — 測れるものを増やせば、判断が良くなる

中間指標の観測系を作ると、最終指標が0のままでも「n件動きました」と報告できてしまう。それは計測資産の存在を計測できていると判定することと同じで、77周の失敗機構そのものである。切り分けが要るなら、既にある段階指標を使えばよい。

## 人ではなく、判断材料を探す瞬間を狙う

**属性で対象を切らない。人は移動して予測できない。固定されているのは「行動する前に判断材料を集める」という行動の方である。**

> 壊した前提 — ターゲットは属性で定義する

450インプレッションのうち、実際に動いたのは1人だった。その人はちょうど自分の製品で同じ決定をしようとしていた。属性が合ったのではなく、判断材料を探している瞬間にいた。この瞬間は解決されて消えることがない。

## 出口は、来た場所から遠い順に並べる

**導線の並びは、挙げられた順ではなく到達経路の実測から決める。最初の出口を、最大の流入元にしない。**

> 壊した前提 — 案内は、挙げられた順に並べればよい

公式サイトへの内部リンクを実際に数えたところ、外から入る経路はほぼ全部が X・GitHub・HORU 経由で、直接来る線は無かった。それなのに最初の出口を X に置いていた。来た場所へ返すのは輪であって、出口ではない。さらにページ本体は判断台帳の抜粋なので、読み終えた人の続きは横移動ではなく全文だった。並べた根拠を成果物に書いていなかったので、この矛盾は実測と突き合わせられないまま残っていた。
